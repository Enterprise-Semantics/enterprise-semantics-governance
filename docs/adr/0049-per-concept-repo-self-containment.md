# ADR-ES-049 ; Per-Concept Repo Self-Containment (Self-Contained Concept Repository Layout)

Status: Accepted
Date: 2026-09-30
Deciders: eaojnr
Decision Type: Structural repository architecture (amendment to ES-ADR-030 §2.1)
Scope: Enterprise-Semantics (org-wide, all 48 concept repositories)
Implements: CR-ES-049
Amends: ES-ADR-030 §2.1 (per-concept repository distribution)

## 1. Context

ES-ADR-030 §2.1 distributed the per-concept-repo architecture such that each `concept-<slug>` repository holds only the `concept.yaml` and a README. All other resources (tests, kits, docs, mappings, examples, visuals, conformance pages) live centrally in `enterprise-semantics-test-probe`, `enterprise-semantics-docs`, `enterprise-semantics-mappings`, `enterprise-semantics-examples`, and `enterprise-semantics-visuals`.

Per user directive 1554547354756063314 (2026-09-30), this distribution is insufficient. Each concept must be self-contained inside its own repository, with exhaustive depth (concept record, kit, tests, illustrations, target architectures, capability maturity models) and breadth (assessment, measurement, conformance).

The current distribution produces 48 concept repos containing only a stub `concept.yaml` and a 6-line README. Stakeholders cannot assess a concept depth, maturity, or fitness for use by cloning a single repository.

## 2. Decision

### 2.1 Self-Contained Layout (amends ES-ADR-030 §2.1)

Each `concept-<slug>` repository SHALL contain the following exhaustive layout:

```
concept-<slug>/
├── README.md                              ; Landing page with quick-jump index
├── concept.yaml                           ; Authoritative concept record
├── kit/
│   ├── kit.yaml                           ; Kit manifest (machine-readable)
│   ├── positive-01.yaml                   ; Positive conformance test 1
│   ├── positive-02.yaml                   ; Positive conformance test 2
│   ├── positive-03.yaml                   ; Positive conformance test 3
│   ├── positive-04.yaml                   ; Positive conformance test 4
│   ├── positive-05.yaml                   ; Positive conformance test 5
│   ├── negative-01.yaml                   ; Negative conformance test 1
│   ├── negative-02.yaml                   ; Negative conformance test 2
│   ├── negative-03.yaml                   ; Negative conformance test 3
│   ├── negative-04.yaml                   ; Negative conformance test 4
│   └── negative-05.yaml                   ; Negative conformance test 5
├── docs/
│   ├── concept.md                         ; Definition, semantic grounding, boundaries
│   ├── conformance.md                     ; CI-generated conformance snapshot
│   ├── target-architectures.md            ; Reference target architectures using this concept
│   ├── capability-maturity-model.yaml     ; 5-level maturity model (Level 0-4)
│   ├── assessment.md                      ; How to assess an instance against the maturity model
│   └── measurement.md                     ; Quantitative metrics + measurement methodology
├── mappings/
│   ├── wsf.yaml                           ; WSF mapping (if exists in central)
│   ├── opendea.yaml                       ; OpenDEA mapping (if exists in central)
│   └── dea-catalogs.yaml                  ; DEA Catalog mapping (if exists in central)
├── examples/
│   └── *.yaml                             ; All concept-specific examples
└── visuals/
    └── *.puml                             ; All concept-specific diagrams (PlantUML)
```

### 2.2 Synchronization Direction

Central repositories remain the canonical source of truth. The per-concept repo is a derived snapshot regenerated by CI on every push to the central repos. Specifically:

- When `enterprise-semantics-test-probe/tests/kits/<slug>/kit.yaml` changes, trigger regeneration of `concept-<slug>/kit/kit.yaml`.
- When `enterprise-semantics-test-probe/tests/<slug>/*.yaml` changes, trigger regeneration of the corresponding `concept-<slug>/kit/positive-NN.yaml` or `negative-NN.yaml`.
- When `enterprise-semantics-docs/concepts/<slug>.md` changes, trigger regeneration of `concept-<slug>/docs/concept.md`.
- When `enterprise-semantics-mappings/mappings/{wsf,opendea,dea-catalogs}/<slug>.yaml` changes, trigger regeneration of `concept-<slug>/mappings/`.
- When `enterprise-semantics-examples/examples/**/<slug>.yaml` changes, trigger regeneration of `concept-<slug>/examples/`.
- When `enterprise-semantics-visuals/docs/diagrams/<slug>/*` changes, trigger regeneration of `concept-<slug>/visuals/`.

### 2.3 CI Implementation

A new workflow `.github/workflows/sync-concept-repos.yml` lives in the `.github` org repo. On any push to main in a central repo, it:

1. Identifies which `<slug>` was affected by inspecting the changed files.
2. Locates the target `Enterprise-Semantics/concept-<slug>` repo.
3. Copies the affected files via the GitHub API (no local clone).
4. Commits with the cardinal author rule and a structured commit message.

The workflow uses only `GITHUB_TOKEN`. No new credentials.

### 2.4 Cardinal Author Rule Preserved

All commits and PRs in this amendment carry `Emmanuel A. Otchere <emmanuel@otchere.com>` as author (cardinal author rule, 2026-09-24).

### 2.5 Capability Maturity Model Standard

All per-concept maturity models follow the same 5-level structure (Level 0 Ad-hoc to Level 4 Adaptive) with consistent criteria categories: Awareness, Definition, Implementation, Measurement, Optimization. Per-level evidence requirements are documented in each concept capability-maturity-model.yaml.

### 2.6 Target Architectures Standard

Each concept has 3 reference target architectures at increasing scales: small (single team / single value stream), medium (single organization), large (multi-organization / ecosystem). Each target architecture specifies: scope, actors, boundary interfaces, evidence of concept instantiation, and known limitations.

### 2.7 Assessment and Measurement Standard

Each concept has an `assessment.md` describing the assessment methodology (evidence required per level, conformance gating, assessor qualifications) and a `measurement.md` describing quantitative metrics, measurement frequency, instrumentation requirements, and reporting format.
